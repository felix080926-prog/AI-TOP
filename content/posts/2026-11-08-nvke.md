英伟达把自家 AI 工厂里管 Kubernetes 的那一层开源了。

最近这几天，NVIDIA Kubernetes Engine（NVKE）以 Apache 2.0 协议放上 GitHub，代码在 dsx-ai-factory 组织下，官方文档挂在 docs.nvidia.com/nvke，最新预览版 v0.24.0-rc.5 于 11 月 5 日发布。它要解决的问题很具体：机房里堆着成千上万张 GPU 的运营商，怎么像云厂商卖托管 Kubernetes 那样，按客户交付互相隔离的集群。消息出来后 heise、AI Weekly 和一批中文技术社区都在转，这个仓库今天一天涨了 123 星，总量 573。

![NVIDIA DSX OS 里 Kubernetes GPU 集群的配置、认证与运维（来源：NVIDIA 开发者博客）](https://developer-blogs.nvidia.com/wp-content/uploads/2026/11/dsx-os-cluster-readiness-featured.webp)

这背后是一个正在成型的趋势：AI 工厂对外卖的东西，从"租你几台机器"变成了"给你一整套能自助扩容的集群"。谁掌握集群的创建、升级、换机和证书续期，谁就握着算力服务的入口。英伟达此前的 Base Command Manager 管的是企业自建的大集群，Run:ai 管的是共享算力池内部的配额切分，按租户对外交付独立控制面这一层一直是空的——现在它补上了。

NVKE 不是又一个 Kubernetes 发行版，也不是 Cluster API 的一个变种，官方给自己的定位是"集群工厂"：一个一次性的种子集群拉起管理集群，管理平面再按需孵化一批互相隔离的工作负载集群，每个都带自己独立的控制面、独立的 etcd 和独立的节点池。客户拿到的是一份 kubeconfig，用 kubectl 干活，看不见背后的机器。

**项目地址：**https://github.com/dsx-ai-factory/nvke

![NVKE 产品家族与组件数据流：NVKR 构建并签名制品发布到仓库，管理平面经 CAPNICo 调用 NICo 供给 GPU 机器，客户用 kubectl 访问工作负载集群](https://raw.githubusercontent.com/dsx-ai-factory/nvke/main/docs/assets/diagrams/product-family.svg)

它落在英伟达 DSX OS 这套栈的中间层：底下的 NICo 负责裸金属发现、刷固件、配网络、供主机；NVKR 从锁定的输入构建并签名节点镜像与组件制品；NVKE 在这些机器上创建和运维集群；再往上是 AICR 提供的加速运行时组合，以及检测 GPU 故障的 NVSentinel。职责切得很干净，NVKE 不碰裸金属管理，也不负责运行客户的工作负载。

两个设计细节值得单独说。一是节点身份：机器加入集群前要用 TPM 走 SPIFFE/SPIRE 完成证明，才拿得到加入凭证，etcd 静态加密可以按集群单独开。二是供应链：镜像和制品由 NVKR 构建、签名并附 SBOM，运维方可以按自己的策略校验签名后再放行。集群本身跑的是上游 Kubernetes、kubeadm 和 Cluster API，CNCF 已认证它产出符合规范的集群，客户原有的工具链和习惯不用改。

想动手的话，本地评估不需要 GPU，也不需要英伟达账号。找一台 Linux 主机（至少 6 核、12 GiB 空闲内存、100 GiB 空闲磁盘，带 Docker 和虚拟 TPM；macOS 走 Colima 虚拟机），核心几步是这样：

```bash
git clone https://github.com/dsx-ai-factory/nvke.git
cd nvke
make -C cli build && export PATH="$PWD/cli/bin:$PATH"
make -C controller capd-up   # kind 集群 + Cluster API + 节点镜像
cd controller && tilt up     # 起管理平面，监听 http://localhost:8080
```

另开一个终端，把 nvkectl 指向管理平面，再创建一个集群：

```bash
nvkectl config set-site --name local --url http://localhost:8080 --kubeconfig "$PWD/local-mgmt.kubeconfig"
nvkectl create cluster -f cli/examples/nico-mock-cluster.yaml
nvkectl get clusters
```

这里的 NICo 由 mock-NICo 顶替，每个工作负载节点就是一个 Docker 容器，整条链路能在单机上跑通。

值得关注，但别急着上生产。官方在预览说明里自己列了一串硬伤：安装后 API 默认监听 30080 端口、走明文 HTTP 且认证关闭，即使手动开启认证，内部也没有授权分级，任何通过认证的调用者都能创建和删除集群；管理集群不能自行升级、扩容或换节点，也没有备份恢复流程；交付给客户的管理员 kubeconfig 因为不轮换 CA，到期前无法吊销。仓库里还挂着几十个未关闭的 issue，其中不乏主干端到端测试挂红这类 P0 问题。

所以现在的合理姿势是：拿一台普通 Linux 机器把评估流程跑一遍，弄清它的接口和运维模型，再决定要不要等它走向生产。对自建智算中心的团队来说，这个项目补的是"按租户对外交付独立 K8s 控制面"这一层——以前基本靠各家自研，现在多了一个来自上游硬件厂商的开源选项。
