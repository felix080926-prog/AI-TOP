AI 编程助手越来越多，但真用起来的人都会碰到同一个问题：塞进上下文里的东西，大多不是模型真正需要的。一次代码搜索返回一百条结果，一段崩溃日志动辄几千行，一份 API 返回的 JSON 层层嵌套——这些全都要按 token 计费，一个不落地灌进模型窗口。账单涨了，答案却没变好。

headroom 干的正是这件事：在工具输出、日志、文件、RAG 分片进入模型之前，先压缩一遍。

**项目地址：**https://github.com/headroomlabs-ai/headroom

![Headroom 把 10,144 token 的日志压缩到 1,260 token，同时保留关键的 FATAL 行](https://raw.githubusercontent.com/headroomlabs-ai/headroom/HEAD/HeadroomDemo-Fast.gif)

它的思路不是"把所有东西总结成一段话"，而是按内容类型用不同的压缩器：JSON 这类结构化的工具输出走 SmartCrusher，源代码走能理解 AST 的 CodeCompressor，普通文本走 Kompress 系列模型。内容先由 ContentRouter 判断类型，再交给对应的压缩器；压缩后 CacheAligner 稳定前缀，让提供商的 KV 缓存能真正命中。最关键的是 CCR 可逆压缩——原文存在本地，模型真需要时能调 headroom_retrieve 取回，不是压完就丢了。

省多少，README 给了实测数字：代码搜索 100 条结果，17,765 token 压到 1,408，省 92%；SRE 故障排查，65,694 压到 5,118，省 92%；GitHub issue 分类，54,174 压到 14,761，省 73%。官方给出的口径更保守：编码 agent 约省 20%，JSON 场景省 60-95%。压缩没有牺牲答案质量——GSM8K 数学推理保持 0.870，TruthfulQA 反而从 0.530 涨到 0.560。

接入方式也够灵活。想改代码就当成库，`compress(messages)` 一行调用；不想改就起个代理，`headroom proxy --port 8787`，任何语言零改动；用 MCP 客户端就挂它的 MCP server，拿到 headroom_compress、headroom_retrieve、headroom_stats 三个原语；还能 `headroom wrap claude` 直接包住已有的 coding agent。

![headroom learn 挖掘失败的会话并写出修正](https://raw.githubusercontent.com/headroomlabs-ai/headroom/HEAD/headroom_learn.gif)

项目到现在攒了 7.2 万 Star，单日还在涨 778，说明被 token 账单和上下文窗口折磨的人确实不少。它适合两类场景：一是跑 coding agent 或 RAG、天天跟 LLM API 账单打交道的团队，压缩能立竿见影地降成本；二是被长上下文窗口卡住的场景，压掉冗余后能塞进更多有效信息。

也要说清楚它的边界：它解决的是"喂给模型的东西太臃肿"这件事，不是魔法。如果根本不在乎 token 成本，或者模型上下文窗口本来就用不满，收益就很有限。但对正在规模化用 agent 的人，这是个方向正确、数据也扎实的选择。

项目地址：https://github.com/headroomlabs-ai/headroom
