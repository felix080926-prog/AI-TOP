做 RAG 的人大多碰过同一个尴尬：知识库里的文档已经改完了，检索出来的还是半天前的内容。常见做法是定时重跑一遍索引，几分钟到几小时一轮，中间那段空窗期，模型答的其实是旧数据。

流处理和 RAG 本来是两套东西：前者用 Flink、Spark 这类引擎跑实时计算，后者用向量库加脚本拼起来。想把「文档一变、索引就跟着变」做成一条真正的流水线，通常得在两边各写一半胶水代码。

Pathway 想干的是把这两件事并进一条管道。它是一个 Python 的 ETL 框架，底层跑的是基于 Differential Dataflow 的 Rust 引擎，做增量计算——数据进来多少，就只重算受影响的那部分，而不是整批重跑。

**项目地址：**https://github.com/pathwaycom/pathway

![Pathway 的监控面板，能看到各连接器的消息量和系统延迟](https://d14l3brkh44201.cloudfront.net/pathway-dashboard.png)

它最值得看的地方有两个。

一是同一份代码既能跑批也能跑流。开发和测试阶段直接读本地文件，上线换成 Kafka 或者数据库，业务逻辑不用重写。连接器覆盖 Kafka、PostgreSQL、GDrive、SharePoint，另外接了一层 Airbyte，能对上三百多个数据源。

二是内置了一整套 LLM 工具。LLM 调用封装、文档解析器、切分器、embedding 都有，还带一个常驻内存的实时向量索引，文档一变索引就跟着更新，不用等定时任务。官方给了几个现成模板：私有化 RAG（Ollama + Mistral）、多模态 RAG、Adaptive RAG——后者按需调整喂给模型的文档数量，官方测试称能在保持准确率的前提下把问答成本压到原来的四分之一左右。

另外，管道状态可以持久化，进程重启或者崩了之后能接着跑；对于迟到和乱序的数据点，引擎会自动重算受影响的结果，而不是丢掉或者算错。官方版给的是「至少一次」语义，企业版提供「恰好一次」。

![Pathway 官方 Adaptive RAG 方案的示意图](https://pathway.com/assets/content/blog/adaptive-rag-plots/visual-abstract.png)

## 装起来只要几步

要求 Python 3.10 以上，装完就能用：

```
pip install -U pathway
```

管道写完调一句 `pw.run()` 就跑起来了，也可以交给 CLI 起多线程：

```
pathway spawn --threads 3 python main.py
```

要上容器的话，官方镜像已经打好了：

```
docker run -it --rm --name my-pathway-app -v "$PWD":/app pathwaycom/pathway:latest python my-pathway-app.py
```

从发布到现在，这个仓库攒了 6.2 万 Star，今天一天又涨了 80 个。

![Pathway 在 WordCount 场景下与其它流处理框架的基准对比](https://github.com/pathwaycom/pathway-benchmarks/raw/main/images/bm-wordcount-lineplot.png)

有一点要留意：Pathway 用的是 BSL 许可证，不是标准的开源许可，商业使用前建议先看一遍具体条款。

客观地说，它的适用场景挺明确：数据一直在变、又需要低延迟拿到结果的管道，比如实时风控、日志告警，以及文档频繁更新的 RAG 服务。如果只是离线跑一批数据、结果隔天出也无所谓，用现成的批处理工具就够了，没必要为这个再引入一套流式引擎。
