**大家好，我是雷达君。**

你打开 Claude Code，一个会话还没开始，系统提示词已经塞进去几万个 Token。MCP 挂上几个，Playwright 的 21 个工具、13,700 个 Token 先占为敬。等你真正开始写代码，上下文窗口已经没了**7%到 9%**。

你明明只想让 AI 帮你改两行代码，它脑子里却塞满了“子代理”“计划模式”“权限审批弹窗”“后台 Bash”“TODO 管理”。

这个行业有个默认假设：AI Agent 功能越多越强。MCP 要有，子代理要有，计划模式要有，权限弹窗要有——全都给你塞进上下文里，你还没开始干活，它已经背上了几万 Token 的包袱。

当所有人都在做加法的时候，有一个叫**PI**的终端编码 Agent 反其道而行之：不支持 MCP、不支持子代理、不支持计划模式、不需要权限弹窗。结果它在**Terminal-Bench 2.0**上打败了几乎所有竞争对手。

它被 XDA Developers 评为“DevOps、编码和日常折腾任务中最喜欢的 AI 应用”。

它就是——**PI**。

## 01 ｜核心逻辑：给你原语，而不是预烹饪好的功能

PI 的核心理念可以用一句话概括：**给你原语（primitives），而不是预烹饪好的功能（features）**。

其他编码 Agent 的迭代路径是不断做加法：内置子代理、内置计划模式、内置 MCP 支持、内置权限审批弹窗、内置后台 Bash、内置 TODO 管理。每加一个功能，系统提示词就膨胀一圈，上下文窗口就被多占一块。

PI 的做法完全相反——它把这些功能全部拿掉。你猜 PI 的系统提示词加工具定义加起来多少 Token？

**不到 1000 个**。

Claude Code 的系统提示词是数万 Token，OpenAI Codex 精简但仍然很长，opencode 基本照抄 Claude Code。PI 只用 1000 个 Token 就搞定了同样的事。

PI 的作者 Mario 的解释是：**当今的前沿模型已经被 RL 训练得足够好了，它们本身就理解编码 Agent 是什么、该怎么做。不需要 10000Token 的长篇大论来教它们工作**。

PI 只给了 AI**4 个工具**：`read`、`write`、`edit`、`bash`——这就是一个完整编码 Agent 所需要的全部。

**一句话：别人在堆功能，PI 在减负担。**

## 02 ｜硬核功能盘点

> 🔗 **GitHub 地址**：https://github.com/earendil-works/pi

### 1. 极简工具集：4 个工具，干所有活

PI 的工具列表短得让人怀疑它是不是真的能干活——read 读文件、write 写文件、edit 精准编辑、bash 执行命令。

就这么 4 个。没有内置子代理，没有 MCP 支持，没有计划模式。但就是这 4 个工具，让 PI 在 Terminal-Bench 2.0 上打败了几乎所有竞争对手。

XDA Developers 的评测说得更直接：PI 用 read、write、edit 和 bash 命令，避免把大量额外输入塞进有限的上下文窗口里。在自托管 LLM 服务器上，这恰恰是最重要的——你不想让一个 Agent 还没开始干活就先吃掉一半的上下文。

### 2. 自扩展：它自己能给自己写插件

PI 最逆天的设计是：**它可以用 LLM 给自己写扩展**。

你连上一个足够强的模型（比如 Qwen3.6-35B-A3B），PI 就能自己设计出有效的扩展。XDA 的测试者用`llama-server + PI`的组合，让 PI 写了一个 Proxmox 扩展，**第一次尝试就跑通了**——而他试过的其他 GitHub 仓库，大部分连把 LLM 连到虚拟化平台都做不到。

“一个能修改自己设计来适应开发需求的编码工具”。这才是真正的“自进化”。

### 3. 极简系统提示词：不到 1000Token，省下来的都是钱

PI 的系统提示词有多短？核心内容就是一段不到 20 行的说明：你是一个专家编码助手，有 4 个工具可用。

对比一下：Claude Code 几万 Token，OpenCode 基本照抄 Claude Code。PI 用不到 1000Token 就把事情做完了。

**省下来的 Token，就是省下来的钱。**

### 4. 三明治架构：核心极简，外层无限扩展

PI 采用了一套“三明治”架构：

- **底层**：`@earendil-works/pi-ai`——统一多提供商 LLM API，支持 OpenAI、Anthropic、Google 等
- **中层**：`@earendil-works/pi-agent-core`——带工具调用和状态管理的 Agent 运行时
- **上层**：`@earendil-works/pi-coding-agent`——交互式编码 Agent CLI

核心极简，外层通过 TypeScript 扩展、Skills、Prompt 模板无限扩展。你可以通过`tmux`派生 PI 实例来实现子代理效果，通过写`PLAN.md`文件来实现计划模式。

> **现实摩擦提醒**：PI 默认以完全 YOLO 模式运行——不限制文件系统访问、不检查 bash 命令、没有权限弹窗。作者的态度非常坦诚：“如果你的 Agent 能写代码、能运行代码，那基本上就 game over 了。”如果你需要更强的边界，官方提供了三种容器化方案：Gondolin 扩展（在本地 Linux 微 VM 中运行工具）、Plain Docker（整个 PI 跑在容器里）、OpenShell（策略控制沙箱）。

## 03 ｜它为什么不需要 MCP？

这可能是 PI 最具争议的设计决策。

其他 Agent 把 MCP 当成标配，PI 明确说不支持。Mario 专门写了一篇博文解释原因。核心问题是**MCP 的上下文开销太大**：

- Playwright MCP：21 个工具，占用**13,700 Token**
- Chrome DevTools MCP：26 个工具，占用**18,000 Token**

每次会话开始，还没干活就先吃掉**7%到 9%的上下文窗口**。而且大部分工具在当前会话中根本用不到。

PI 的替代方案极其简单：**把功能包装成 CLI 工具，每个工具附带一个 README.md，Agent 在需要时才读取（渐进式披露），通过 bash 调用 CLI 工具**。

好处是显而易见的——**按需加载，只在需要时付出 Token 成本**。

**不是 MCP 不好，是 PI 选择了另一种更省 Token 的方式来做同样的事。**

**简单说：Claude Code 和 Cursor 是“给你一个装满功能的瑞士军刀”，PI 是“给你一块铁，你自己磨成想要的样子”**。

## 05 ｜典型场景和避坑

**适合谁用？**

- **在自托管 LLM 上跑编码 Agent 的开发者**：PI 的极简设计让它在有限的上下文窗口里依然高效
- **觉得主流 Agent 太臃肿、想自己控制一切的极客**：给你原语，你自己组装
- **想让 AI 自己给自己写扩展的高级用户**：PI 的 LLM 自扩展能力是独一份的
- **喜欢终端原生体验的开发者**：PI 是一个纯粹的终端编码 Agent

**不推荐给谁？**

- **需要开箱即用、不想折腾配置的普通用户**：PI 的默认 YOLO 模式和极简设计需要你花时间去理解它的哲学
- **需要企业级权限管理和审计的场景**：默认没有权限系统，需要自己加容器化
- **重度依赖 MCP 生态的开发者**：PI 明确不支持 MCP

## 06 ｜快速上手指南（2 分钟）

**第 1 步：安装**

```bash
npm install -g @mariozechner/pi-coding-agent
```

**第 2 步：配置模型**

```bash
pi config set provider openai
pi config set api-key YOUR_API_KEY
```

支持的 Provider 包括 OpenAI、Anthropic、Google、Fireworks AI 等。

**第 3 步：启动**

```bash
cd /path/to/your/project
pi
```

你会看到一个交互式终端界面，输入你的任务，PI 会开始工作。

> **验证安装成功**：运行`pi --version`，如果能返回版本号，说明安装成功。

## 07 ｜总结

PI 解决了一个被大多数人忽视的问题：**AI Agent 的系统提示词和内置功能，正在吃掉你越来越多的 Token。**

Claude Code 几万 Token 起步，挂几个 MCP 再吃掉上万 Token。你还没开始写代码，上下文窗口已经空了一大半。PI 用不到 1000Token 的系统提示词和 4 个核心工具，在 Terminal-Bench 2.0 上打败了几乎所有竞争对手。

不是功能越多越强，是**负担越少越高效**。

在 AI Agent 越来越臃肿的今天，PI 选择了一条完全相反的路——做减法，减到只剩 4 个工具、1000 个 Token。然后让你自己用 LLM 去扩展它，让它长成你想要的样子。
